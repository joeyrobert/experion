# NNUE and strength work: September 2026

This session began from the failures recorded in [`nnue-session-findings.md`](nnue-session-findings.md). The goal was to make Experion stronger against Crafty while keeping the engine fully Crystal, UCI compliant, and testable.

The most useful result is a new ENN4 network format and trainer. The old ENN3 input summed white and black feature perspectives. That representation has a real collision: a white rook and a black rook on the same square can produce the same combined input. No amount of additional data can recover information that is absent from the input. ENN4 preserves the two perspectives separately, uses color and mirrored-square features, clipped per-perspective activations, and adds a trainable material/PSQT lane. Runtime inference and accumulator updates remain in Crystal.

The training machine at `joey@192.168.2.46` was used through the existing PyTorch CUDA 12.4 container. Its RTX 3060 was occupied by `llama-server`; the service was stopped for training and was not restarted automatically. The CCRL 40/15 archive was extracted and parsed into 474,326 training and 25,684 validation positions for the 500k run. A larger pass produced 2,850,749 training and 149,253 validation positions. Labels are CCRL search scores before annotated quiet moves, expressed from White’s perspective. Splitting is by game hash and positions are deduplicated globally.

The 500k and 3M exports were independently checked against a scalar Python reader. On 300 held-out positions, the 500k export differed from the float model by 0.96 cp mean absolute error and 2.29 cp maximum. The 3M export differed by 0.94 cp mean absolute error and 2.24 cp maximum. Sanity positions were correctly signed: the 3M net scored a rook about +539 cp, two rooks +1086 cp, and an extra black queen -937 cp. These checks establish serialization and basic material behavior; they do not establish playing strength.

Several engine correctness defects were fixed. NNUE accumulator updates now make the move before applying the delta, so the child board is used for king-bucket rebuilds. Quiescence now handles repetition, the fifty-move rule, stalemate, and quiet checking moves correctly. Singular extensions are applied only to the TT move and require a sufficiently deep TT entry. Quiet/en-passant classification and root move reduction use the parent position. Search cancellation uses a reference object containing the atomic flag; Crystal’s `Atomic` is a value type, so passing it directly had copied the stop state between workers. Packed shared-TT loads and stores are atomic. `bestmove 0000` is emitted for terminal positions.

The classical evaluator was corrected in four places: passed-pawn front spans now follow each pawn’s direction, rook-file pawn tests use the correct occupancy projection, duplicated dynamic terms were removed, and tempo is awarded to the side to move. The changes are covered by focused evaluator tests.

Validation currently passes 655 Crystal examples. The UCI regression tool checks the handshake and `EvalBlend` declaration, one and four threads, immediate stop, node-limited search, NNUE enable/disable, terminal positions, and clean quit. The Crystal ENN4 path matched the independent Python integer evaluator on 102 positions, including castling, promotions, en passant, and king moves.

The old baseline at `10+0.1`, 40 games versus Vice, scored 2-37-1 (6.25%). The corrected evaluator screening match versus Vice at `2+0.02`, 40 games, scored 11-25-4 (32.5%, -127 Elo ±114). The same corrected build scored 3-36-1 versus Crafty at that short control (8.75%, -407 Elo ±356). The repaired one-thread search build scored 20-15-5 versus Vice (56.25%, +44 Elo ±105) and 6-32-2 versus Crafty (17.5%, -269 Elo ±156). A four-thread Crafty run reached 3-28-2 after 33 games before being stopped; it was trending worse and is not treated as a completed benchmark. This is a positive result against Vice but no evidence of beating Crafty; the Crafty interval is wide and the time control is only a screening run. Longer confirmation matches are required before attributing Elo to any individual change. The benchmark harness runs opponents sequentially, stores separate PGNs and logs, records binary/network/opening hashes, and rejects incomplete games.

The 3M NNUE run was selected at epoch 10 by validation loss because later epochs overfit. It is not enabled by default and should only be used with `EXPERION_NNUE` or the UCI `Use NNUE` option. The previous ENN3 and king-bucket checkpoints remain comparison artifacts and should not be treated as production nets. The current evidence does not support the claim that NNUE beats classical evaluation or Crafty yet. The strongest defensible conclusion is that the input collision and several search/UCI correctness bugs are fixed, a reproducible stronger-label training path exists, and classical search/evaluation changes produced the first measurable short-control improvement against a ladder engine.

Follow-up work should run the queued 40-game screening matches to completion, then repeat any promising candidate at `10+0.1` with `CONC=1`. NNUE should be screened on STS and then matched only if it is at least neutral at low blend. Crafty-labeled data needs a larger fraction or a stronger positional training target before expecting it to exceed the classical evaluator.
